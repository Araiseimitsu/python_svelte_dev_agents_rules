# 開発ワークフロー

作業手順と完了条件の正本。安全確認は `AGENTS.md` §11、委譲は同 §12、確認の要否は同 §2 に従う。

## 1. 通常の進め方

1. 目的、関連ルール、既存実装と差分を確認する。
2. 複数箇所や仕様に関わる変更は、対象と方針を短く伝える。小さな修正に計画書は不要。計画の共有と承認要求を混同しない。
3. 承認範囲内で実装し、必要な文書も更新する。承認が必要な操作だけ保留し、準備・調査は進める。
4. 差分を自己レビューし、変更に応じて検証する。不備を修正し、影響する検証を再実行する。
5. 結果、実行した検証、未解決事項を簡潔に報告する。完了した作業に継続確認を挟まない。

長い作業では判明したことと次に確かめることを短く共有する。新しい指示は進行中の目的に反映し、中止・置換の明示がなければ元の目的も維持する。
長時間のビルド・テストはバックグラウンド実行してよく、結果は必ず回収する。依存する操作や同じファイル・環境を変更する処理は順序を守る。

## 2. 完了条件

- 依頼の範囲を満たし、無関係な差分やユーザーの変更の破棄がない。
- `AGENTS.md` §9 の区分に応じた検証を実行し、結果を確認している。コード変更は関連テストと設定済みの lint・型チェック、ビルドに影響する場合はビルドも確認する。
- UI は必要な表示・操作を実際に確認する。文書のみの変更は内容・参照・整合性と差分確認でよく、アプリの全テストは不要。
- 検証手段が無い場合は利用可能な手動確認を行う。環境や権限で検証できない場合は未検証の項目と理由を明示し、検証済みと表現しない。

関連検証が通った後は、新しい変更・失敗・懸念がなければ同じ検証を繰り返さない。既存の失敗は今回の変更による失敗と区別し、隠したり無関係な修正を広げたりしない。

## 3. テストファースト

業務ロジック・判定・データ変換は、先に期待する振る舞いのテストを作り、意図した理由で失敗することを確認してから実装する。
バグ修正は自動化に適する場合に再現テストを先に作る。UI・環境依存など自動化が適さない場合は再現手順と修正後の実行結果で検証する。
テストは振る舞いと境界条件を確かめ、実装をそのまま写しただけの検査を増やさない。

## 4. デバッグ

エラーと再現条件を確認し、仮説に対応した変更で検証する。原因調査のための実験は製品への恒久修正と区別する。
同じ仮説・手順で3回失敗したら、その手順の反復を止めて根拠と前提を再調査する。ユーザーの判断やアクセスが必要になった場合は、試したこと・判明事項・必要情報を報告する。

## 5. 明示依頼された反復レビュー

通常の修正・再検証を超えて独立したレビュー工程を周回する運用を依頼された場合に適用する。

1. 実装と関連検証を行う。
2. 要求・不具合・安全性をレビューする。委譲の指定がなければ自身で行う。
3. 必須修正を直して関連検証を行い、指摘が残れば再レビューする。

必須修正がなくなれば終了する。最大3周で解決しない場合は、残る問題と必要な判断を報告する。任意の改善提案は収束条件にせず、依頼範囲を広げない。承認範囲は周回によって拡大しない。

## 6. Git 運用

着手時と終了時に差分を確認する。コミットは依頼やプロジェクトの運用に従い、対象ファイルを明示して無関係な変更を混ぜない。
ブランチ運用があれば従い、必要な場合のみ作業ブランチ・worktree を用いる。単純な文書修正で作業環境を儀式的に増やさない。
