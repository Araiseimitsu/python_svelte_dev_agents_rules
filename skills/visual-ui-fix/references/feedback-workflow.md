# 視覚フィードバックの収集

## 内蔵ブラウザを使える場合

1. 対象URLと、loading・empty・error・successなど確認すべき状態を固定する。
2. 対象の表示幅を記録する。複数幅の指示がある場合はコメントごとに区別する。
3. ユーザーが要素を指定する場合は要素選択、複数要素を含む意図には領域選択を使う。
4. 色、背景、テキスト、フォント、余白など具体値を試す場合はAdjustでプレビューする。
5. 自由コメントには、問題の説明だけでなく希望する結果も含めてもらう。
6. ユーザーが反映を指示した時点の保存済みコメントだけを確定変更として扱う。

ブラウザコメントは画面上の対象を示す証拠であり、安定したソース位置ではない。必ずDOMとリポジトリの実装を対応付ける。

## 変更項目の整理

各コメントについて、次を作業メモとして保持する。固定ファイル形式への書き出しは不要である。

- URLとルート
- 画面状態と表示幅
- 対象要素または領域
- 元の見た目・文言
- 希望する結果
- Adjustで確定した値
- ページ限定か共有変更か
- hover、focus、disabledなど関連状態

同じ対象へのコメントは、両立するものだけまとめる。古いコメントと新しいコメントが衝突する場合は、新旧を推測せず確認する。

## CLIまたはIDEの場合

Kimi WebBridgeが利用可能なら [cli-browser-workflow.md](cli-browser-workflow.md) に従い、実ブラウザへ同梱Overlayを一時注入する。Overlayの変更一覧を取得するまではソースを変更しない。Kimi WebBridgeを利用できない場合は、環境が提供するPlaywrightまたはブラウザ操作機能を確認する。永続的な対話セッションを作れない場合は、存在しない機能を装わず、注釈付きスクリーンショット、URLと文章による指定の順で代替する。

画像だけの場合は、対象要素の特定に必要なルート、表示幅、表示文言を確認し、Visionによる推定を明示する。

## スコープ管理

- 一度の反映は、レビュー可能な一画面または密接に関連する少数のコメントに留める。
- コメント外の美観改善を便乗させない。
- 外部サイトや本番環境では、閲覧・検査とソース変更の対象を混同しない。
